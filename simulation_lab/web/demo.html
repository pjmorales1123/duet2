Engineering log

Everything we tried to get here, including what did not work. Ordered the way the pipeline runs: build a verified teacher, record data from it, fine-tune a policy on that data, then optimize the policy for Intel hardware.

Simulator & expert teacher

  1. Pose-aware cabinet workflow. Items spawn scrambled in a cabinet zone with randomized pose; the grasp is planned from the live object pose rather than a fixed hard-coded pick point.
  2. Fixed skill ordering. Skills run bottle → plate → mug → fork → spoon. This is not cosmetic: the fork and spoon approach paths physically cross where the plate lands, so an out-of-order run fails real path-clearance checks. The UI unlocks one skill at a time to match.
  3. Two-arm pour hand-off. Right arm relays the bottle to a shared point, left arm re-grips and lifts it, right arm grips the mug and holds it still, left arm tilts ~51° and pours. Verified by grasp force, cup stillness and bottle-mouth-in-cup geometry — not by a timer.
  4. Mug target position, second attempt. A revised mug position estimated from an overhead screenshot looked right but broke the pour: 2 of 3 pour tests failed with the gripper outside the arm's useful reach. Reverted to the measured position that passes 3/3 pour tests and 7/7 layout tests. Screenshot geometry is a hypothesis; the physics test is the answer.
  5. 10-seed robustness sweep. Every seed randomizes spawn offsets, object rotation, lighting brightness and table tint. Pour succeeds on 10/10 after the table is set.
  6. HD gallery by replay. Recorded runs are re-rendered at 1280×960 by replaying the saved action trajectory from the saved initial physics state, so the HD video is the same run you can drive live, not a separate take.

Policy training & Intel optimization

  1. Dataset from the verified teacher. Only episodes the teacher's physical checks marked successful are kept. 50 placement episodes (5 skills × 10 seeds), then 10 pour episodes added — 60 episodes / 7 151 frames, published as duet-micro-v1 in LeRobot format.
  2. SmolVLA fine-tune, v1 → v2. lerobot/smolvla_base fine-tuned end to end, 7 000 steps at batch 32. AMP had to be disabled — bf16 and GradScaler were incompatible on the training GPU — which cost throughput but kept the run stable.
  3. CPU inference tuning. Flow-matching denoising steps cut from 10 to 5, torch threads pinned to cores − 2 so the physics loop keeps its own core, and the checkpoint is preloaded at server start. Before preloading, the first click always failed: the cold model load outran the task-submission timeout.
  4. OpenVINO IR conversion, attempt 1 — failed. openvino.convert_model with the legacy TorchScript tracer died inside transformers' attention-mask builder (sdpa_mask, IndexError: tuple index out of range) while tracing the SmolVLM vision encoder. Not our model's bug — a tracer/library incompatibility.
  5. OpenVINO IR conversion, attempt 2 — in progress. Re-running through torch.export (dynamo=True) instead of the legacy tracer, on the Intel Core Ultra machine that is also the deployment target. The action-chunk model is wrapped behind a flat seven-tensor interface (two images, two image masks, language tokens, language mask, state) captured from a real inference call, so example inputs are measured rather than guessed.
  6. Honest status. Conversion is still being validated at the time of writing. The bar we set for calling it done is not "the converter returned without an error" — it is that the IR model reproduces the PyTorch checkpoint's action output on identical input. Until that comparison passes, this page will not claim it.

Why the expert demo is further along than the VLA

They are two stages of one pipeline, not two competing entries. The expert teacher is a scripted controller with real physical verification at every step — grasp force, contact, clearance, final-pose geometry — and it exists first because it is what generates trustworthy training data. Only runs it certifies as successful become episodes.

The VLA is trained on that output, and it has had one small dataset and one short fine-tune. It reproduces the teacher's motion style and responds to language and pixels for real, but 60 episodes is not enough for reliable millimetre placement, so it misses targets that the teacher hits every time. That gap is the honest current state, and it is a data-and-training-time gap rather than an architectural one: the same pipeline scales by recording more teacher episodes.

Judging aid: the Expert tab is where to look for end-to-end task completion and the two-arm pour hand-off. The VLA tab is where to look for genuine language-and-vision-conditioned control. Both run live in this browser against the same MuJoCo simulator — nothing on this page is a recording unless it is explicitly labelled as one.
